You are updating an existing Personal Development Tool built in Replit.

The tool already has a User Management section with:
- User list
- Name
- Email
- Role
- Department
- Status
- Edit/delete actions
- New User button

Do not rebuild the tool from scratch. Extend the existing User Management area and preserve the current design language, styling, navigation and existing functionality unless a change is specifically required below.

OBJECTIVE

Build a flexible user hierarchy and permissions system so access to employee development data is controlled by role, reporting line, team membership and optional additional permissions.

The hierarchy must be scalable. Do not hard-code the logic as simply “Manager = parent” and “Director = grandparent”. Instead, build a recursive reporting structure using a “Reports To” relationship so the system can support any number of management layers in future.

CORE USER ROLES

Create the following user roles:

1. Employee
- Can only access their own personal development information.
- Existing rules controlling what employees can and cannot edit in their own profile must remain unchanged.

2. Manager
- Can access their own information.
- Automatically gets full view and edit access to all users who report directly or indirectly to them through the reporting hierarchy.
- Managers may report to another Manager or Director.

3. Director
- Can access their own information.
- Automatically gets full view and edit access to all users below them in the reporting hierarchy, including direct reports and all indirect reports at any depth.

4. Admin
- Full system access.
- Can create and edit users.
- Can assign roles.
- Can create and manage teams.
- Can change reporting lines.
- Can grant additional access permissions.
- Can view the full organisational hierarchy.
- Can access the audit log.
- Can use “View as User” functionality.

REPORTING HIERARCHY

Add a “Reports To” relationship for every user.

This must be the primary source of truth for organisational hierarchy and default permissions.

Example:

Andy Davis, Director
→ Andrew Collins, Manager
   → Harry Mann, Employee
   → Chloe Bennett, Employee
   → Matt Gilham, Employee

In this example:
- Andrew can fully view and edit Harry, Chloe and Matt.
- Andy can fully view and edit Andrew, Harry, Chloe and Matt.
- Harry can only access Harry’s own information.

The hierarchy must work recursively so there is no fixed limit on how many levels exist.

When Admin changes a user’s “Reports To” field:
- The hierarchy must update automatically.
- Access permissions based on hierarchy must recalculate automatically.
- The employee’s historical development data must remain unchanged.

Never delete or reset:
- Competency evidence
- Probation history
- Development history
- Promotion objectives
- Reviews
- Check-ins
- Completed records
- Historical notes
just because a user changes manager, team or reporting line.

ADDITIONAL ACCESS

Additional access must sit on top of the reporting hierarchy and must not replace it.

Create:

1. Additional View Access
Admin can grant view-only access to:
- Individual users
- Entire teams

2. Additional Full Edit Access
Admin can grant full view and edit access to:
- Individual users
- Entire teams

The UI should clearly distinguish between:
- Access gained through the reporting hierarchy
- Additional view access
- Additional edit access

If a user already has full edit access through their reporting hierarchy, do not create duplicate permissions.

TEAM MANAGEMENT

Create a new Admin section called “Teams”.

Admin should be able to:
- Create a team
- Rename a team
- Deactivate/archive a team
- View members of a team
- Add or remove users from teams

Examples of teams might include:
- Data Centre Recruitment
- Technology Recruitment
- Operations
- Marketing

Important:
Team membership alone must NOT give someone access to another user’s development data.

Access comes from:
1. Reporting hierarchy
2. Additional View Access
3. Additional Full Edit Access

Do not create a separate Team Owner or Team Manager permission structure. The reporting hierarchy remains the source of truth.

PERMISSION LOGIC

Create a single reusable permission system rather than duplicating checks throughout individual pages.

The system should be able to answer questions such as:

canViewUser(currentUser, targetUser)
canEditUser(currentUser, targetUser)

Permission precedence should work roughly as follows:

ADMIN
Full access to all users.

SELF
Users can access their own information according to the existing self-edit rules already built into the Personal Development Tool.

HIERARCHY
Managers and Directors receive full view/edit access to all direct and indirect reports beneath them.

ADDITIONAL FULL EDIT ACCESS
Grants view and edit access.

ADDITIONAL VIEW ACCESS
Grants view-only access.

NO MATCH
No access.

Do not weaken any existing permission restrictions relating to which fields an employee may edit on their own profile.

SECURITY REQUIREMENTS

Do not rely only on hiding UI buttons.

Permissions must be enforced at the data/backend/API level as well as in the frontend.

A user must not be able to access another employee’s information by:
- Editing a URL
- Changing an ID
- Calling an endpoint directly
- Manipulating frontend state

Use the current authentication system and extend it safely.

Prevent privilege escalation.

Only Admin users should be able to:
- Change roles
- Change reporting lines
- Grant additional permissions
- Manage teams
- View the audit log
- Use View as User
