## Intended behavior

A user may hold multiple roles simultaneously. The roles are represented and submitted as a string array, for example:

```ts
["manager", "admin"]
```

The supported selectable roles in the Live form are:

| Value | Label |
|---|---|
| `employee` | Employee |
| `manager` | Manager |
| `director` | Director |
| `admin` | Admin |
| `ld` | L&D |

The previous implementation treated a user as having one role. The form used a single `role` enum, defaulted to `employee`, and converted a user’s roles array to one “primary” role when editing. The Users list likewise displayed and filtered by one derived role. Saving the form sent `roles: [values.role]`, so editing a multi-role user could discard every role except the selected primary role.

The new implementation must preserve all selected roles when editing and saving, display each role wherever roles are shown, and match a role filter against membership in the full roles array.

## Form and role helpers

In the Admin user form:

- Use `roles: string[]` in the form state, with validation requiring at least one selected role.
- Default a new user to `roles: ["employee"]`.
- Render a checkbox for each supported role. Multiple checkboxes may be selected; the last selected role cannot be removed because the form requires at least one.
- When editing, initialize from a copy of the user’s entire `roles` array. Do not collapse it to a primary role.
- Toggling a role must be immutable: selecting adds it only if it is not already present; deselecting removes that role without changing the others.
- Use the roles array in both create and update payloads. The Live helper clones the array when constructing the payload, so the payload does not alias the form’s array.

The Live helpers have these semantics; implement equivalent functions using Development’s existing types and conventions:

```ts
function getActiveAdminUsers<T extends {
  roles: readonly string[];
  isActive: string;
}>(users: readonly T[]): T[] {
  return users.filter(
    user => user.isActive === "active" && user.roles.includes("admin"),
  );
}

function getEditableRoles(roles: readonly string[]): string[] {
  return [...roles];
}

function isRoleSelected(roles: readonly string[], role: string): boolean {
  return roles.includes(role);
}

function setRoleSelected(
  roles: readonly string[],
  role: string,
  selected: boolean,
): string[] {
  if (selected) {
    return roles.includes(role) ? [...roles] : [...roles, role];
  }

  return roles.filter(currentRole => currentRole !== role);
}

function buildRolesPayload(roles: readonly string[]): { roles: string[] } {
  return { roles: [...roles] };
}

function matchesRoleFilter(
  roles: readonly string[],
  roleFilter: string,
): boolean {
  return roleFilter === "all" || roles.includes(roleFilter);
}

function getRoleLabels(
  roles: readonly string[],
  labels: Record<string, string>,
): Array<{ role: string; label: string }> {
  return roles.map(role => ({ role, label: labels[role] ?? role }));
}
```

Preserve roles that are already in an edited user’s array, including an unknown role not represented in the five visible checkboxes. The role-selection helpers should not discard unrelated roles when a known role is toggled.

The current Live API-facing form sends `roles` as an array for both create and update. These commits do not change the API server or database schema. Inspect Development’s API contract and adapt to it; do not add unrelated backend or schema changes.

## Users list and table

The Users list must:

- Display one badge for every role on a user.
- Filter by whether the user’s roles array contains the selected role. The `all` filter matches every user.
- Keep the existing search, employment/recruitment, status, team, manager, and action behavior. Search does not search role text in the Live implementation.

The Live implementation uses human-readable labels in the directory: Employee, Manager, Director, Admin, and L&D. Unknown roles display their raw role string. Badge variants are employee/L&D secondary, manager default, director outline, admin destructive, and unknown roles secondary. A user with no roles gets no role badge in this directory table.

Live extracted the table from `UsersPage` into `UsersTable` to make the table easier to test. This component extraction is not required if Development can implement and test the behavior cleanly in its current structure. If extracting it, preserve the existing loading and empty states, non-role columns, and callbacks.

## Teams, Hierarchy, and `RoleBadges`

Teams and Hierarchy views must show all of a user’s roles, not a primary role. The Live implementation uses a shared `RoleBadges` component with a `team` or `hierarchy` context:

- It accepts optional or nullable roles and renders every role in array order.
- If roles are missing or empty, it displays `employee`.
- It displays the raw role values (`admin`, `manager`, etc.), styled uppercase; it does not use the directory’s human-readable labels.
- Team context uses secondary badges for every role.
- Hierarchy context uses destructive for admin, default for manager, outline for director, and secondary for other roles.
- Badges are placed in a wrapping container so multiple roles can fit.

Development may adapt the exact styling to its UI system, but it must retain the distinct team/hierarchy behavior and show every role. The Live hierarchy badges also use `shrink-0`; the badge sizing, typography, and other layout classes are presentational details.

## Admin identity picker

An account qualifies for the Admin identity picker only when:

```ts
user.isActive === "active" && user.roles.includes("admin")
```

This recognizes an Admin who also has other roles. In Live, that predicate already existed inline before the helper was extracted; the related change moved it into `getActiveAdminUsers` and added unit coverage. Inactive admins and active non-admin users must not appear.

The Live commit also extracted and restyled the picker. Its card, copy, spacing, and button layout changes are incidental; keep Development’s existing visual design unless a small change is required to display eligible accounts. The separate “View As User” control in `AdminLayout` lists active users generally; it is not the Admin identity picker.

Do not add or claim saved-admin-role revalidation as part of this work. The Live commits listed here do not recheck an already stored admin identity when that user loses the Admin role.
